# 自動 Account Rotator
[English (original)](ACCOUNT_ROTATOR.md) · [Deutsch](ACCOUNT_ROTATOR.de.md) · [Español](ACCOUNT_ROTATOR.es.md) · **日本語** · [简体中文](ACCOUNT_ROTATOR.zh-CN.md)

> 本ドキュメントは英語原文の翻訳です。相違がある場合は英語版が正となります。

オプションの Account Rotator は、許可されたログインを別々のアカウントとして保持します。有効にしている間は、新しくログインに成功するたびに、それが別のアカウントとして保存されます。対応しているリクエストでは、選択中のアカウントで処理を続けられない場合に、kit が保存済みの別のアカウントを試すことがあります。再試行が成功するとは限りません。出力が始まる前に起きた一時的なネットワークやゲートウェイの障害は、まず同じアカウントで再試行されます。この再試行だけでアカウントが切り替わることはありません。

この機能がアカウントを作成したり、利用枠をリセットしたり、プロバイダーのルールを回避したりすることはありません。ログインをインポートしても、新しい利用枠は付与されません。アクセスが認められているアカウントだけを使ってください。

## 有効化と無効化

この機能はデフォルトでは無効です。ターミナルでは、セットアップが次のように尋ねます。

> Do you want to activate the Account Rotator feature? [y/N]

`y` と答えると機能が有効になり、kit がすでに使えるログインはそのまま保持されます。`n` または Enter では無効のままです。セットアップは回答を保存し、再び尋ねることはありません。`zcode-kit setup --reask` を実行すると、もう一度尋ねられます。ターミナルがない場合、セットアップはこの設定を変更しません。無人インストールでは、セットアップに `--account-rotator y` または `--account-rotator n` を渡すか、`ZCODE_KIT_ACCOUNT_ROTATOR` を `y` または `n` に設定してください。

この機能はいつでも切り替えられます。

```sh
zcode-kit accounts enable
zcode-kit accounts disable
```

どちらのコマンドも、変更を反映するために、この kit の実行中のプロキシを再起動します。無効にしても、保存済みのアカウントは残ります。

## アカウントの追加と管理

別のアカウントを追加するには、もう一度ログインします。ZCode Desktop がすでに使っているログインをインポートすることもできます。

```sh
zcode-kit auth login zai
zcode-kit auth login zai --import
zcode-kit accounts
```

インポートが読み取るのは、現在共有されている Desktop の認証情報であり、新しく作成されたアカウントではありません。Desktop 0.16.9 では、暗号化された `credentials.json` が存在する場合、それが正となります。以前の `config.json` に切り替わるのは `credentials.json` が存在しない場合だけです。ファイルの破損、復号用シークレットの誤り、サポートされていない有効なプロバイダーの場合は、古いログインを黙ってインポートするのではなく、エラーになります。インポーターは、現在有効な `zai`/`start-plan` のログインを読み取り、`start-plan` には明示的に設定されたプランが必要です。`coding-plan` では、上の通常の OAuth ログインを使ってください。読み取り専用の Desktop インポーターは、API キーの解決や作成を行いません。Desktop の共有認証情報を変更することもありません。

アカウントの一覧には、次の管理コマンドで使う ID が表示されます。

```sh
zcode-kit accounts pause <ID>
zcode-kit accounts resume <ID>
zcode-kit accounts remove <ID> --yes
```

一時停止と再開は、新しいリクエストに適用されます。すでに実行中のリクエストは、そのアカウントを使い続けます。`--yes` を付けずに `remove` を実行すると、何も変更されず、`--yes` を付けて実行し直すよう求められます。アカウントを削除しても、Desktop のログインには影響しません。

使える保存済みアカウントがない場合、kit が無関係なアカウントや許可されていないアカウントに切り替えることはありません。その場合、リクエストは失敗することがあります。

そのほかのコマンド：

| コマンド | 用途 |
| --- | --- |
| `zcode-kit accounts --json` | アカウントの一覧を JSON で表示します。認証情報は含みません。 |
| `zcode-kit accounts --live` | 実行中のプロキシから読み取った、アカウントの実行時の状態を表示します。 |
| `zcode-kit accounts quota` | 実行中のプロキシから読み取った、プール内のすべてのアカウントの利用枠を表示します。 |
| `zcode-kit accounts explain --model MODEL --operation OP` | 設定上、あるモデルと操作（`inference`、`billing`、`quota`、`async`）に使える保存済みアカウントと、それ以外のアカウントが除外される理由を表示します。読み取るのは設定とストアだけです。 |
| `zcode-kit accounts doctor [--json]` | 設定とアカウントストアを読み取り専用でチェックします。 |
| `zcode-kit accounts unlock [--force]` | アカウントストアに残された放棄済みのロックを削除します。まだ保持されているロックや読み取れないロックは、`--force` を付けた場合だけ削除されます。 |

## 再ログイン

同じ OAuth ユーザー ID でログインすると、既存のアカウントがその場で更新されます（トークンは新しくなり、ラベル、一時停止、クールダウンは保持されます）。同一の認証情報を再インポートしても結果は変わりません。プロバイダーとプランの区別は維持されます。

Desktop からのインポートには、検証済みのユーザー ID がない場合があります。その場合、デコードした JWT の subject が一致しても、それは重複の可能性を示すだけで、認証情報を上書きしてよいという意味にはなりません。トークンが変わっている場合、コマンドは黙って置き換えることも、重複として追加することも拒否し、既存のアカウントの名前を示します。置き換えるつもりなら、そのアカウントを明示的に指定してください：`zcode-kit auth login zai --import --account ID --replace`（OAuth の場合は `--import` を省略します）。subject が上流の `userId` フィールドに昇格されることはありません。

`--account ID` を指定すると、そのユーザーがすでに別の ID で保存されていても、常に指定した ID で保存されます。その場合、ログイン時にもう一方の ID を示すメモが表示され、`zcode-kit accounts doctor` は `same_identity_accounts` を報告します。このような別名はユーザーの利用枠を共有するため、容量は増えません。それでもローテーターは別のエントリとして扱います（元のアカウントの後に試すこともあります）。削除するには `zcode-kit accounts remove <ID> --yes` を使います。

## アカウントの状態

```sh
zcode-kit accounts health
zcode-kit accounts health --json
```

アカウントごとに 1 行の表を表示します。列は、アカウント ID、判定、プラン、利用枠（利用枠パッケージごとの残量/合計、割合、リセット時刻）、最後に使われた時刻です。`*` は有効なアカウントを示します。表の下には `usable: N of M` とプール全体の合計が表示されます。このコマンドには実行中のプロキシが必要です。プロキシが動いていない場合、すべてのアカウントが `unknown` になり、`zcode-kit proxy start` を実行するよう案内されます。終了コード 0 は、少なくとも 1 つのアカウントが `ok` または `low` であることを示します。1 は、現在使えるアカウントがないか、ライブデータを取得できないことを示します。

判定の一覧です（優先度の高い順）。表では `auth_error` と `no_quota_data` が `auth error` と `no quota data` と表示されます。JSON 出力では下の名前のままです。

| 判定 | 意味 |
| --- | --- |
| `paused` | 自分またはポリシーによって一時停止されています。 |
| `blocked` | プロバイダー、プラン、または許可リストのポリシーによって除外されています。 |
| `expired` / `invalid` | ログインの有効期限が切れているか、現在の設定では使えません。 |
| `auth_error` | 課金サービスがログインを拒否しました（401/3012）。もう一度ログインしてください。 |
| `exhausted` | 利用枠エラーの後のクールダウン中で、表示された時刻まで続きます。クールダウンが始まる前に、kit は間隔を広げながら同じアカウントで再試行します（デフォルトは 1 秒、4 秒、10 秒、20 秒、30 秒後で、リクエストが約 1 分間保留されることがあります）。ゲートウェイは、まだ利用枠が残っている別の残高パッケージ（空になった日次パッケージの横にあるイベント付与分など）から再試行に応答することがあります。この再試行の間隔は、アカウントが 1 つだけのインストールにも適用されます。Account Rotator モードでは、再試行が無効になっている場合、拒否された場合、または別のエラーで失敗した場合にもクールダウンが適用されます。利用枠を使い切ったことが確認されるまで待つのは、アカウントが 1 つの場合の再試行メモだけです。`ZCODE_PROXY_QUOTA_RETRY_DELAYS_MS` で調整または無効化できます（カンマ区切りのミリ秒。`0` は 1 回だけ即座に再試行、`off` は無効化。最大 6 項目で、各項目の上限は 60 秒。10 進数の数字だけを使えます。無効な値の場合はデフォルトの間隔に戻ります。プロキシの起動/再起動時にそのまま渡されます）。 |
| `duplicate` | 対象のアカウントの中に、検証済みの OAuth ID が同じアカウント、または同一の認証情報があります。利用枠は 1 回だけ問い合わせて合計されます。デコードした JWT の subject だけで、問い合わせが省略されることはありません。 |
| `no_quota_data` | サービスは応答しましたが、現在このアカウントの利用枠パッケージを報告しませんでした。正常な状態であることは確認されていません。 |
| `empty` | すべての利用枠パッケージを使い切っています。 |
| `low` | 少なくとも 1 つのパッケージの残りが 10% 未満です。 |
| `ok` | 利用枠が残っており、使えます。 |
| `unknown` | このアカウントについて、完全なライブの応答がありません（プロキシが停止している、利用枠の問い合わせが失敗した、またはパッケージが不完全な数値を報告した）。使えるアカウントとして数えられることはありません。 |

JSON には、アカウントごとに `probeSource`（`live`、`duplicate`、`error`、`not_probed`）が含まれます。一時停止中のアカウントやポリシーで除外されたアカウントは表示されますが、問い合わせは行われません。課金の応答にそれらが含まれていなくても、利用枠がゼロとは解釈しません。

コスト：1 回の実行で、一意のアカウントごとに最大 2 件の課金リクエスト（残高とプレビュー）を送り、結果は 15 秒間キャッシュされます。モデルへのリクエストは送らず、CAPTCHA も解かず、トークンも更新しません。

実行中のプロキシがアカウントのメタデータ（クールダウン、最後の使用）をストアに書き込めない場合（別のプロセスがロックを保持している場合や、一時的な I/O エラーの場合）、変更は保持され、0.25 秒、1 秒、4 秒、15 秒後にバックグラウンドで書き直されます。これを待つリクエストはなく、次の変更があればいずれにしても再び書き込まれます。変更がまだディスクに書かれていない間、`zcode-kit accounts doctor` は `runtime_changes_unsaved` を表示します。破損したストアに対しては再試行しません。
