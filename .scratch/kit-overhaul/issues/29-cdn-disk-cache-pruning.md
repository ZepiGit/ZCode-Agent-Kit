# 29: CDN disk cache pruning

**Blocked by:** 25 (Bounded-collection module; CDN memory cache and stall counters bounded)

**Status:** ready-for-agent

Model: sol

Risk: medium

ADR: 0009

**What to build:** The disk cache stays ≤ 256 MB (oldest first), pruning only entries already expired at max(14 days, configured TTL), at start and after each write, skipping temp files and files being written, tolerating `ENOENT`, safe with several installations sharing the directory.

- [ ] Temp-dir tests (seam 3/6): size bound, expiry-only pruning, temp/in-progress files skipped, concurrent pruners with vanishing files never throw or corrupt.
- [ ] Retention-pruning migration replayed twice is a no-op.
- [ ] An entry 15 days old under a configured TTL of 20 days is kept; an entry 21 days old is pruned (Round 2 Q3 condition 2).

Nothing throws out of a prune. What is fetched, from where, and the bytes/sha256/`fetchedAt` served are unchanged (B1) for every workload that fits within 256 MiB, because only expired entries are removed below the cap.

  - **Decisions** (smallest choices where spec/ADR are silent):
    1. 256 MB is 256 MiB (268,435,456 bytes), like the memory tier's MiB budget.
    2. The after-write prune checks the pruner's view (last scan + own writes) and scans again only when the view is above the cap, holds an entry at the age limit, or is ≥ 60 s old. A full scan per write costs ~4 ms per 400 entries on Linux (`t29-scripts/scan-cost.ts`), ~5 s over the replay's 1,300 writes and likely far more on Windows. Effect: another installation's writes are counted at the latest at this process's first write 60 s after its last scan (and that installation prunes after its own writes).
    3. TTL 0 disables the disk tier, so that installation does not prune at all.
    4. Raw bodies without an envelope (64-hex from kits up to v0.2.31, 40-hex sha1 from the earliest kits) are entries aged by mtime; this kit never serves them. The 60 s grace protects in-place writers.
    5. Temp files are never deleted and not counted, as the spec says, so a temp file left by a crashed writer stays (pre-existing; not bounded by this ticket).
    6. The cache's own `invalidate()` does not update the view (it can only overcount, which triggers an earlier scan).
