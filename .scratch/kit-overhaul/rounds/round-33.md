## Q1 — how is windows S4 `stale-lock-after-ctrl-c` judged?

Facts: ticket 17 makes a start-lock holder that is ended by SIGINT/SIGTERM/SIGHUP (Windows: Ctrl-C, Ctrl-Break, console close via Node's own listeners) remove its own lock while the record on disk is still its own, then exit as the signal would have. On linux S4 `stale-lock-after-ctrl-c` goes 5/8 → 0/8 in all 9 branch runs. On windows the S4 scenario's "Ctrl-C" is `child.kill("SIGINT")`, which Node maps to `TerminateProcess`: no handler runs, so the trial measures a hard kill (a crash), not a Ctrl-C. The name therefore cannot go GREEN on windows from any kit change, and 17 keeps it listed. Crash recovery on windows is already judged by other S4 names (`respawn-recovers-despite-stale-lock` and the takeover by proof from 16). Delivering a real console control event to a child needs `GenerateConsoleCtrlEvent` with the child in its own process group/console (e.g. a small helper started with CREATE_NEW_PROCESS_GROUP that sends CTRL_BREAK_EVENT, since CTRL_C_EVENT cannot target a process group), which is test-harness work in tests/memory only.

Recommendation: keep the check's purpose (a user's Ctrl-C must not leave a stale lock) and make the windows trial send a real console event: a follow-up memory-loop ticket adds a windows helper that starts the holder in a new process group and sends CTRL_BREAK_EVENT (17's handler covers Ctrl-Break), with a self-test proving the event reached the child's handler; until it merges, windows S4 `stale-lock-after-ctrl-c` stays listed under 17 → re-owned to the new ticket, and the trial is labelled in the summary as "TerminateProcess (crash), not a console event" so nobody reads it as a Ctrl-C result. Ticket 17 may merge with the name listed and its other windows criteria met in its pre-merge run.
