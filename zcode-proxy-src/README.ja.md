# ZCode Proxy
[English (original)](README.md) · [Deutsch](README.de.md) · [Español](README.es.md) · **日本語** · [简体中文](README.zh-CN.md)

このコンポーネントは、ZCode Agent Kit に同梱されるローカルモデル
プロキシを提供します。セットアップは Kit が管理し、アシスタントとの
連携は同意を得た場合だけ設定します。

## ZCode Agent Kit での使用

[メイン README](../README.ja.md) に記載されたセットアップとモデルの
コマンドを使用してください。同梱ソースのバージョンとローカル変更は
[コンポーネントマニフェスト](../MANIFEST.md) に記載されています。Kit には
Node.js 24 以降が必要で、プロキシは Bun で起動します。固定している Bun の
バージョンは 1.4.2 です。

## Desktop ログインのインポート

`zcode-kit auth login zai --import` は、Desktop の現在の共有ログイン情報を読み込みます。
Desktop 0.16.9 の `credentials.json` が存在する場合は、それが正式な参照元です。
従来の `config.json` にフォールバックするのは、このファイルが存在しない場合だけです。
認証情報の破損、誤ったシークレット、未対応のアクティブプロバイダーでは、黙って
フォールバックしません。アクティブな `zai`/`start-plan` のインポートでは、
`start-plan` に明示的なプラン設定が必要です。`coding-plan` では通常の OAuth ログインを使用します。
インポートはアカウントの作成、利用枠のリセット、API キーの取得・作成を行いません。
[アカウント管理](../docs/ACCOUNT_ROTATOR.md)も参照してください。

## CAPTCHA ソルバーとキャッシュ

ソルバーはメモリ上限 300 MB（`solver.memoryCapMB`）の独立したプロセスで動作し、
CAPTCHA ウィンドウを一度に一つだけ実行します。上限の 80 % に達したとき、または
100 回解いた後に、新しいプロセスに置き換えられます。
[docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md) の「The solver process」を参照してください。
最初にトークンを一つ準備し、需要に応じて最大四つまで保持します。
従来の並列実行設定はこの処理能力に制限されます。プロバイダーのレート制限による
一時停止は維持され、待機中の処理、キャッシュ無効化、診断ハッシュで回避できません。

`CAPTCHA_CDN_CACHE_TTL_MS` はメモリとディスクの両方の CDN キャッシュを制御します。
既定値は `86400000` ms（24 時間）で、`0` から `2147483647` までの整数のみ有効です。
無効な値はエラーになり、`0` は両方のキャッシュの読み書きを無効にします。
`CAPTCHA_CDN_CACHE_DIR` で独立したキャッシュディレクトリを指定できます。
Kit が管理するプロキシは、両方の環境変数を子プロセスに渡します。ディスクへの書き込みは
アトミックなエンベロープ形式を使い、取得時刻のない古いエントリや途中で切れたエントリは
拒否します。メモリへの昇格時も、元の取得時刻に基づく経過時間を保持します。

診断では、読み込んだ各アーティファクトの来歴をアトミックに記録し、ウィンドウごとに
実際に読み込んだバイト列の SHA-256 ハッシュを示します。来歴が不明な場合は明示します。
`Last-Modified` は過去のバイト列との同一性を証明しません。保存済みのプロバイダー
スクリプトを静的に調べるには、インストール先のヘルパーを使用してください。

```sh
node <installation>/zcode-proxy-src/captcha-compatibility.mjs <saved-script> [retrieval-epoch-ms]
```

取得時刻が分かる場合は epoch ミリ秒で指定します。このヘルパーはファイルを読み、
ハッシュと互換性マーカーを報告するだけです。スクリプトを実行せず、エンドツーエンドの
CAPTCHA 成功を証明するものでもありません。従来の診断用バイトコード VM 書き換え
（`PE_PATCH`）はバンドル破損が再現されたため削除され、機密性のある DBT 引数ダンプ
（`CAPTCHA_DUMP_DBT`）も削除されました。これらのスイッチは使用しないでください。
ソルバー、安全性チェック、呼び出し可能な `show` の代替経路は維持されています。
デバッグ診断はメタデータのみを扱います。

## 応答と再試行

プロキシは、変換対象のストリームや JSON エラー応答を解釈する前に gzip、deflate、
Brotli を展開します。空または展開できないバッチ応答は、空の成功応答ではなく
`upstream_invalid_response` として通知します。プロキシは自身の作業ディレクトリを
呼び出し元のワークスペースとして提示しません。`ZCODE_IDENTITY_ENV_CWD` は明示的な
上書きとして維持されます。

出力前の一時的な障害は、同じアカウントで最大 3 回再試行します。予算は公式
クライアントより小さくなっています。

- 再試行するもの: 接続の拒否やリセット、HTTP 500、502、503、504、524、529、429、
  公式クライアントが再試行するゲートウェイのエラーコード。
- 再試行しないもの: ゲートウェイの判定（クォータ、残高、CAPTCHA、モデル、認証）、
  リクエストのエラー、出力開始後の障害。
- 待ち時間は増えていきます。最初の再試行の前が約 1 秒で、その後は毎回 2 倍に
  なります。`ZCODE_PROXY_TRANSIENT_RETRY_UNIT_MS` は単位（最初の待ち時間の半分）を
  ミリ秒で指定します（既定 500、上限 10000）。`off` にすると、接続が確立しなかった
  場合の再試行だけを残します。
- 再試行のたびにアカウントを再確認します。`Retry-After` は 15 秒まで尊重し、
  それを超える場合はクライアントに渡します。
- 最初のコンテンツイベントの前に失敗したストリーム（`overloaded_error` などの
  エラーイベントや切断）も同じように再試行します。その場合、クライアントは最初の
  コンテンツイベントが届いた時点で（最大 15 秒後に）レスポンスヘッダーを受け取ります。
- start-plan では、レスポンスや切断の後の再試行ごとに新しい CAPTCHA トークンを
  取得します。
- 強制されたクライアントセッション用の順序付きトランスポートは、レスポンス前に
  切れた接続を fetch 経路と同じように再試行します（同じアカウント。クォータの
  フェイルオーバーが別のアカウントで再送することはありません）。

`message_stop` なしで終わったネイティブの Anthropic ストリームには、最後に
`api_error` 型の `event: error` フレーム 1 つを付加します。メッセージは
`upstream_incomplete`、読み取り失敗時は `upstream_stream_error` を示します。
未完成の最後のフレームは破棄するので、クライアントは無言の途切れではなく
解析できる障害を受け取ります。

## 停止、再起動、過負荷

- **停止。** Kit のマネージャーは、ループバックのリスナーへの認証付きリクエスト
  （`POST /__kit/stop`、プロキシキーと起動ごとに作られる停止トークン）でプロキシに
  停止を依頼します。プロキシは新しいリクエストに HTTP 503 と `Retry-After` で
  応答し、実行中のリクエストには完了まで最大 6 秒を与え、まだ開いているものを
  打ち切って、10 秒以内に終了します。マネージャーが自分でプロセスを終了するのは、
  その 2 秒後にまだ動いている場合だけです。
- **過負荷。** プロキシが同時に保持するリクエストボディは最大 64 MiB です。
  それを超えるリクエストは待機し（最大 64 件、それぞれ最大 15 秒）、その後
  HTTP 503 と `Retry-After: 2` で応答されます。429 にはなりません。処理中の
  リクエストがないプロキシは、必ず 1 件を受け付けます。上限は
  `proxy/config.yaml` の `server.admission.maxInFlightMB`（1 から 4096）、または
  `ZCODE_PROXY_ADMISSION_MAX_INFLIGHT_MB` で設定します。開いているレスポンス
  ストリームには上限がありません。
- **メモリ。** プロキシは 15 秒ごとにメモリを測定します。3 回連続で 512 MB を
  超えると、ログに警告を書きます。3 回連続で 1024 MB を超えると、Kit の
  マネージャーに再起動を依頼し、マネージャーが受け付けた後に停止処理に入ります。
  マネージャーが受け付ける再起動は 15 分間に最大 3 回です。拒否された場合、
  プロキシは動作を続けます。しきい値は `proxy/config.yaml` の `health.memory` に
  ある `softLimitMB`、`hardLimitMB`、`samples`、`sampleIntervalSeconds` です。
- **応答しないプロキシ。** プロキシのメインスレッドが 45 秒間動かなかった場合、
  プロキシは Kit のマネージャーに再起動を依頼し、自分で終了します。
- **Kit のマネージャーなしの場合。** Kit のマネージャーが起動していないプロキシは
  停止リクエストを受け付けず、再起動されることもありません。メモリの上限を超えても
  ログに書くだけで動作を続けます。メインスレッドが動かなくなった場合は自分で
  終了し、停止したままになります。

## ログ

Kit のマネージャーが起動したプロキシは、出力を 1 つのライターを通して
`logs/proxy.log` に書きます。ライターは 5 MB でファイルをローテーションし、
古いファイルを 1 つ `proxy.log.1` として残します。プロキシキー、停止トークン、
トークンの形をした文字列は `<redacted>` に置き換えます。macOS と Linux では、
ログファイルはモード `0600`、ログディレクトリはモード `0700` で作成されます。
ログは `zcode-kit proxy logs [n] [--level warn|error] [--grep <text>]` で
読めます。Kit のマネージャーなしで起動したプロキシは、これまでどおり端末に
出力します。

## セキュリティ

このプロキシは、信頼できるローカル環境での使用を想定しています。
ローカル端末上でのみ実行し、ログイン情報と設定データを保護して
ください。一部のプロバイダー認証チャレンジでは、OS のサンドボックス
なしでプロバイダー提供の JavaScript が実行される場合があります。
ローカル接続でも、そのコードは隔離されません。サービスを端末外に
公開しないでください。詳細は[セキュリティポリシー](../SECURITY.md)を
参照してください。
